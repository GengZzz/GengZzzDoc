# 缓存：用一致性换性能的艺术

几乎每个扛住高并发的系统背后都有缓存。它能把一次几十毫秒的数据库查询，变成零点几毫秒的内存读取，性能轻松提升一个数量级。但工程界也流传一句话——「缓存是万恶之源」。本篇要回答的就是：**缓存为什么这么有效，它的代价是什么，以及怎么用好它而不被它反噬？**

## 痛点：数据库为什么扛不住

数据库的瓶颈通常不在「算」，而在「读盘」和「连接数」。一个热门商品详情页，每秒可能有上万次请求，如果每次都去查数据库：

- 磁盘 I/O 和复杂查询让单次响应变慢；
- 连接池被打满，请求开始排队，延迟雪崩式上涨。

问题的关键是：**这上万次请求，查的往往是同一批数据**。让数据库重复劳动去返回几乎一样的结果，既慢又浪费。

## 缓存为什么有效：局部性原理

缓存之所以成立，靠的是一条朴素规律——**局部性原理（locality）**：程序访问的数据是不均匀的，**少数热点数据被反复访问**。把这批热点放到更快的介质（内存）里，绝大多数请求就不必再碰数据库。

::: tip 心智模型
把数据库想成城郊的**中央大仓库**（容量大、但取货慢），缓存就是楼下的**便利店**（容量小、但即拿即走）。你要的东西大概率便利店就有（命中），偶尔没有才跑一趟大仓库（未命中），顺便把它补到便利店里。
:::

衡量缓存效果的核心指标是**命中率（hit rate）**——请求中有多大比例被缓存直接满足。命中率越高，数据库越轻松。这个类比也提示了缓存的边界：便利店货架有限（内存有限），放不下所有商品，所以**必然涉及「放什么、淘汰什么」**，后面会谈到。

## 最常用的模式：Cache-Aside（旁路缓存）

最广泛使用的缓存模式叫 **Cache-Aside（旁路缓存）**，由应用代码自己负责读写缓存。

**读流程：**

```text
1. 先查缓存
2. 命中 → 直接返回
3. 未命中 → 查数据库 → 写回缓存 → 返回
```

```java
Object read(String key) {
    Object value = cache.get(key);
    if (value != null) {     // 命中
        return value;
    }
    value = db.query(key);   // 未命中，回源数据库
    cache.set(key, value, TTL); // 回填缓存，并设过期时间
    return value;
}
```

**写流程**：更新数据库，然后**删除**缓存（而不是更新缓存）：

```java
void update(String key, Object value) {
    db.update(key, value);
    cache.delete(key);       // 让下次读时自然回填，而非主动改缓存
}
```

为什么写的时候是「删除」而不是「更新」缓存？因为**删除是惰性的、代价更低**：如果这条数据之后没人读，就没必要白白算一遍新值写进去；等真有人读时，让读流程自然回填即可。这也更不容易出错——主动更新缓存会引入额外的并发写顺序问题。

## 缓存的本质代价：一致性

缓存的所有麻烦，根源是同一件事：**同一份数据现在有了两个副本**（数据库一份、缓存一份），而你没法让两次写「原子地」同时完成。于是在极短的时间窗口里，两者可能不一致。

::: warning 常见误区
有人以为「先更新数据库，再删缓存」就万无一失了。其实在高并发下仍可能不一致：比如读请求恰好在「另一个写请求删了缓存、还没更新完数据库」的间隙回填了旧值。完全的强一致需要更复杂的手段（如分布式锁、延迟双删），而大多数业务选择**接受短暂的最终一致**。
:::

这就是缓存的本质——**它是一笔交易：用「一致性」换「性能」**。理解这一点，你就抓住了所有缓存设计的主线：你不是在追求完美，而是在**决定能容忍多大、多久的不一致**，并据此选策略。对商品库存这类敏感数据，容忍度低；对文章阅读数这类数据，容忍度很高。

## 三大经典故障：穿透、击穿、雪崩

这三个名字常被混淆，但区别很清晰——关键看**「缓存里有没有这个 key」和「失效的是一个还是一片」**：

| 故障 | 含义 | 根因 | 对策 |
| --- | --- | --- | --- |
| 穿透 | 查一个**根本不存在**的数据 | 缓存和数据库都没有，每次都打到库 | 缓存空值；布隆过滤器拦截非法 key |
| 击穿 | 某个**热点 key 恰好过期**的瞬间 | 大量请求同时未命中、同时回源 | 互斥锁只放一个去回源；热点永不过期 |
| 雪崩 | **大量 key 同时过期**或缓存宕机 | 失效时间集中、整层缓存挂掉 | 过期时间加随机抖动；缓存高可用 + 限流降级 |

记忆要点：**穿透**是「查不存在的」（缓存帮不上忙），**击穿**是「一个热点的瞬间空窗」（点），**雪崩**是「一大片同时失效」（面）。

## 淘汰策略：内存满了删谁

便利店货架有限，缓存内存也有限。放满后再写入，就要按策略淘汰旧数据：

- **LRU（最近最少使用）**：淘汰最久没被访问的，假设「最近用过的还会再用」，最常用。
- **LFU（最不经常使用）**：淘汰访问次数最少的，更适合访问频率稳定的场景。
- **TTL（过期时间）**：到期自动删除，是兜底的「数据保鲜期」。

Redis 同时支持这些策略，可按 `maxmemory-policy` 配置。

## 什么时候不该用缓存

缓存不是越多越好。它增加了系统复杂度和一致性风险，下列情况要慎用：

- **写多读少**的数据：缓存命中率低，还要不停失效，得不偿失；
- **强一致要求**的场景（如账户余额、扣款）：短暂不一致不可接受时，宁可直接读库或上更重的方案；
- **数据量小、查询本身就快**：直接查库即可，引入缓存只是徒增复杂度。

记住：**加缓存是为了解决已经存在的性能问题，而不是预防一个还没出现的问题。**

## 选型：先想清楚你在换什么

| 决策点 | 选项 | 怎么选 |
| --- | --- | --- |
| 写时如何处理缓存 | 删除 vs 更新 | 默认删除（惰性、少错），高读频且更新代价高时才考虑更新 |
| 能容忍的一致性 | 最终一致 vs 强一致 | 看业务：阅读数→最终一致；余额→强一致或不缓存 |
| 淘汰策略 | LRU / LFU / TTL | 通用选 LRU，叠加 TTL 兜底 |
