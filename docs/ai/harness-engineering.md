# Harness Engineering：用自动护栏守住质量

一个项目随着提交变多，质量总会悄悄滑坡：文档格式五花八门、提交信息无规律、空页面上了线、坏代码合进主分支。本篇要回答一个问题——**如何让项目自动拦住低质量改动，而不依赖每个人时刻自觉？** 这正是 harness engineering（工程化质量护栏）要解决的。

## 痛点：靠自觉的规范注定会失效

很多团队的「规范」是一份 `CONTRIBUTING.md` 加一句口头约定。问题在于：人会忘、标准会漂移、review 永远滞后且累人。规范一旦只靠自觉，时间会把它磨平。

这不是危言耸听。就拿本仓库在引入护栏前的真实状态举例：

- 根目录躺着误生成的 `nul` 文件和一个 **3.9 MB** 的开发日志，没人记得清理；
- VitePress 配置 `config.ts` 膨胀到 **1644 行**，导航和侧边栏全堆在一起；
- 对存量文档跑一次 markdownlint，报出 **3549 个**格式问题；
- 提交信息风格各异，没有统一格式。

没有任何一处是「故意」做坏的——它们都是**在没有护栏时，自觉随时间失效的自然结果**。

## 什么是 harness engineering

harness 这个词，原意是马的「挽具」、安全「带」，在工程里也指测试用的「夹具」（test harness）。harness engineering 借用这个意象：**给项目套上一套夹具，让它只能按规范的方式被改动**——把「应该怎么做」从文档里的劝告，变成机器自动执行的约束。

它的设计哲学可以用一个词概括：**防呆（poka-yoke）**。这是源自丰田生产体系的概念，核心是**让做错的事变难、让做对的事成为默认且最省力的路径**。生活里到处是防呆设计：USB-C 插头正反都能插（你不可能插反）、微波炉开门自动断电、安全带没系就持续报警。

::: tip 心智模型
harness = 给开发流程做「防呆设计」。好的护栏不是靠提醒你别犯错，而是让你**想犯错都难**。
:::

**类比的边界**：防呆护栏拦得住「机械性的低级错误」（格式、命名、漏配置），但拦不住「这个设计合不合理」这种需要判断的问题——那是 code review 的职责。护栏让 review 不必再浪费精力盯格式，从而专注真正重要的判断。

## 核心机制：分层防御 + shift-left

护栏不是一道关，而是**一串关卡**。一个改动从你敲下键盘到上线，会依次穿过多层，每层拦住不同的问题：

<HarnessLayersDemo />

为什么要分层，而不是设一道「终极大关」？因为存在一条铁律——**问题越晚被发现，修复越贵**。这就是 shift-left（把质量左移）：尽量把拦截点往「离开发者最近」的地方推。

| 层 | 触发时机 | 反馈速度 | 拦截什么 | 漏过的代价 |
| --- | --- | --- | --- | --- |
| 编辑器 | 保存时 | 即时 | 缩进、行尾、基础格式 | 几乎为零 |
| 提交钩子 | `git commit` | 秒级 | 格式、提交信息规范 | 低 |
| CI 流水线 | push / PR | 分钟级 | 全量 lint、构建、死链 | 中 |
| 部署门禁 | 合并到主分支 | 部署级 | 构建失败即不发布 | 高（已接近线上） |

各层**各司其职**：靠前的层快、给即时反馈，但只能看到局部（如只看改动的文件）；靠后的层慢，但覆盖全、且不可绕过。多层叠加形成冗余——任何一层漏掉的，下一层兜底。

## 怎么搭：从最小到完整

护栏不必一步到位。从一个能跑的最小版开始，再逐步加固。

### 第一步：最小可运行

最朴素的护栏，就是把一条校验命令同时挂到「本地脚本」和「CI」上：

```json
// package.json
{
  "scripts": {
    "lint": "markdownlint-cli2"
  }
}
```

```yaml
# .github/workflows/ci.yml
- run: npm ci
- run: npm run lint # CI 里跑同一条命令
```

此时已经有了最关键的一环：**坏改动进不了主分支**（CI 不过就不能合并）。但反馈要等 CI 跑完，偏慢。

### 第二步：把反馈左移到提交时

加上 [husky](https://typicode.github.io/husky/) 管理 Git 钩子，配合 [lint-staged](https://github.com/lint-staged/lint-staged)——**只校验本次暂存的改动文件**，所以很快：

```json
// package.json
{
  "lint-staged": {
    "**/*.md": "markdownlint-cli2 --fix",
    "*.{ts,vue,css,json}": "prettier --write"
  }
}
```

```bash
# .husky/pre-commit
npx lint-staged
```

注意这里用了 `--fix` / `--write`：**能自动修的就别只报错**。让护栏顺手把问题修掉，而不是把活儿甩回给开发者，这是降低摩擦的关键。

::: warning 版本说明
husky 9 起，钩子就是 `.husky/` 下的普通 shell 脚本（不再需要 `npx husky add` 那套旧写法）。本文基于 husky 9。
:::

### 第三步：约束提交信息

再加 [commitlint](https://commitlint.js.org/) 校验提交信息符合 [Conventional Commits](https://www.conventionalcommits.org/)：

```bash
# .husky/commit-msg
npx --no-install commitlint --edit "$1"
```

到这里，护栏就从「编辑器 → 提交钩子 → CI → 部署门禁」连成了完整的一串。

## 深入：真正的难点是设计取舍

搭一套护栏不难，难的是让它**既守得住质量、又不惹恼开发者**。几个关键取舍：

**严格度 vs 开发体验。** 护栏太松形同虚设；太严则误报频发、拖慢节奏，最后被人想方设法绕过。对存量项目尤其要小心——本仓库首次跑出 3549 个 markdown 告警，其中约 69% 是表格管道空格这类纯样式噪音。处理方式不是硬修 3549 处，而是**收敛规则、增量治理**：把样式类、解析器敏感的规则降为非阻断，自动修复结构性问题，最终把基线降到 0 error。存量先放宽、增量严控，是对待老项目的务实姿态。

**钩子可被绕过，所以 CI 才是真理。** Git 钩子能用 `--no-verify` 一键跳过——这意味着**本地钩子只是「快速反馈」，绝不是「最终防线」**。真正不可绕过的兜底必须在 CI：哪怕本地钩子被跳过，CI 会用同一套规则再拦一次。一句话——**不信任本地，真理在 CI**。

**噪音是头号杀手。** 一旦误报多到让人习惯性忽略，护栏就死了。宁可先放宽、再逐步收紧，也不要一上来就把人淹没在红色报错里。信任一旦失去就很难重建。

::: tip 一个真实的例子
本仓库的 `commit-msg` 钩子刚上线，就立刻拦住了一次真实错误——一条提交信息因为命令写法问题混入了多余字符，导致 subject 为空，被钩子直接打回。这恰恰证明护栏在工作。**当护栏第一次拦住你时，正确的反应是「修问题或修规则」，而不是 `--no-verify` 跳过它**——后者等于亲手拆掉自己的护栏。
:::

## 常见误区

::: warning 常见误区

- **「装了 husky 就安全了」**：钩子可被绕过，没有 CI 兜底等于没有护栏。
- **「规则越多越严越好」**：误报和噪音会摧毁开发者对护栏的信任，反而更糟。
- **「一次性把存量全部修干净」**：会产生巨大的 diff、阻塞正常开发；应收敛存量、严控增量。
- **「报错就 `--no-verify` 跳过」**：这是在拆护栏。钩子失败应排查根因，而非绕过。
  :::

## 选型：护栏不是银弹，三者互补

把「质量保障」全押在护栏上也是误区。它和文档约定、code review 各有定位：

| 手段 | 强制力 | 反馈时机 | 适合拦什么 | 局限 |
| --- | --- | --- | --- | --- |
| 文档约定（CONTRIBUTING） | 无（靠自觉） | 阅读时 | 传达「为什么」与理念 | 会被忘记、不强制 |
| 自动护栏（harness） | 强（机器执行） | 提交 / CI | 机械性、可判定的规则 | 拦不住需要判断的问题 |
| Code Review | 中（靠人） | PR 阶段 | 设计合理性、可读性、业务正确 | 慢、累、依赖评审者水平 |

理想组合是：**护栏兜住所有机器能判定的事，把人的注意力解放出来**，让 review 专注于机器判断不了的设计与权衡，文档则负责解释这些规则背后的「为什么」。
