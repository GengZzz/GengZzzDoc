# Harness Engineering：给大模型造一副「身体」

同样调用 GPT 或 Claude，有的产品能让它自主改完一个仓库的 bug，有的连一次多步骤任务都跑不顺。差距常常**不在模型**——大家用的底座差不多——而在模型外面那层包裹它的软件支架。本篇要回答的就是：**这层支架（harness）到底是什么，为什么它正成为比「换更强的模型」「调 prompt」更关键的杠杆，以及怎么把它设计好。**

::: tip 术语
**Harness**（原意「马具 / 挽具 / 测试夹具」）在 AI 语境里，指**包裹在大模型外面、把模型接入真实世界并驱动它完成任务的那层代码**，也叫 **agent harness（智能体外壳/支架）**。注意它和软件工程里 CI 质量门禁意义上的 harness 是同名不同概念。
:::

## 痛点：模型只是「大脑」，光有大脑不会做事

大语言模型（LLM）本质上只做一件事：**给定一段文字，预测下一段文字**。它没有手、没有眼睛、没有记忆、也没有「执行」的能力。你直接问它「帮我把这个项目的测试跑通」，它只能**描述**该怎么做，却没法真的去读文件、跑命令、看报错。

所以很多人优化 AI 效果时会撞墙：

- 一味**换更强的模型**——可同一个强模型，在不同工具手里表现天差地别；
- 拼命**调 prompt**——但再好的指令，也喂不进它没见过的代码、连不上它该调用的工具。

问题的根源是：**你只升级了「大脑」，却没给它配「身体」**。让大脑能感知环境、动手操作、记住进展、并在出错时自我纠正——这一整套，就是 harness 要解决的。

## 什么是 harness engineering

如果说模型是发动机，**harness 就是发动机之外的整辆车**——底盘、变速箱、方向盘、仪表、刹车。一台再强的发动机，没有传动系统也寸步难行。harness engineering，就是**设计和打磨这套「让模型真正跑起来」的工程**。

换一个更贴切的类比：**模型是大脑，harness 是身体加感官加环境**。

```text
       ┌─────────────────────────────────────┐
       │              Harness（身体）          │
       │   ┌─────────┐   提示/上下文            │
       │   │  模型    │ ◄──────── 该看什么       │
       │   │ (大脑)   │ ────────► 想做什么       │
       │   └─────────┘   工具调用                │
       │        ▲                │              │
       │        │ 观察结果        ▼              │
       │   ┌────┴────────────────────────┐     │
       │   │  工具 · 环境 · 记忆 · 护栏     │     │
       │   └──────────────────────────────┘     │
       └─────────────────────────────────────┘
```

**它和 prompt engineering 不是一回事**——prompt engineering 是「**这一句话怎么写**」，是 harness 的一个零件；harness engineering 是「**整个系统怎么决定该发哪句话、暴露哪些工具、如何循环、如何管理上下文、如何验证结果**」。后者的杠杆大得多。

## harness 由什么组成

一个 harness 通常包含五个部分。其中最核心的是**智能体循环（agentic loop）**——它把「预测文字」变成「持续行动」：

<AgentHarnessLoopDemo />

1. **智能体循环（loop）**：模型提议一个动作 → harness 真正执行 → 把结果喂回模型 → 模型据此决定下一步，如此往复直到任务完成。这是把「一次问答」升级成「自主干活」的引擎。
2. **工具（tools）**：模型能调用的能力——读写文件、执行命令、搜索、查数据库。harness 负责定义工具（名字、描述、参数）、执行它、并做沙箱与权限控制。
3. **上下文管理（context）**：每一轮该往模型有限的上下文窗口里塞什么——系统提示、历史、检索到的资料、工具返回。塞满了还要压缩、摘要、跨会话记忆。**这是 harness 工程的头号难题**。
4. **护栏与验证（guardrails）**：模型的输出不能盲信——校验工具参数、危险操作要确认、出错要重试、循环要有上限。
5. **环境（environment）**：模型实际作用的世界——文件系统、终端、浏览器、API，乃至其它智能体。

## 为什么 harness 正成为新的杠杆

一个反直觉但关键的事实：**同一个模型，套上不同的 harness，能力差距可以非常大**。在 SWE-bench、terminal-bench 这类「让 AI 自主解决真实工程任务」的评测里，分数高低很大程度取决于 harness 怎么设计，而非只看用了哪个模型。

你日常用的 Claude Code、Cursor 这些工具，底层模型彼此相近，**真正拉开差距的正是 harness**——谁更会给模型喂对上下文、给对工具、管好循环。

更深一层的判断是：**随着底座模型越来越强，竞争的杠杆正从「选哪个模型」「调哪句 prompt」上移到「造什么样的 harness」**。模型把「思考」做得越来越好，剩下没解决的，恰恰是「怎么把思考接到真实世界」——那是 harness 的地盘。

::: tip 一个就在眼前的例子
你现在用来读这篇文档的 Claude Code，本身就是一个 harness：它给模型管理上下文（`CLAUDE.md`、按需读文件）、暴露工具（编辑/命令/搜索）、跑智能体循环、在危险操作前要权限、上下文满了自动压缩。换掉里面的模型，它还是同一套 harness。
:::

## 设计原则：难点全在取舍

搭一个能跑的 harness 不难，难的是让它**既放得开模型的能力、又兜得住它的不可靠**。几条核心原则：

**上下文是瓶颈，要的是「对」不是「多」。** 上下文窗口有限，而且越长，模型对中间信息的注意力越容易衰减（俗称「lost in the middle / 上下文腐烂」）。所以不是把所有资料一股脑塞进去，而是**精挑细选**——只给当前这一步真正需要的。这件事大到自成一门，叫 **context engineering（上下文工程）**。

**紧的反馈回路，让模型自己纠错。** harness 最大的价值之一，是把**真实的执行结果**（命令输出、报错、测试结果）喂回给模型。模型看到「我刚才那步报错了」，就能自我修正——这正是 agentic loop 比「一次性生成」强大的根源。回路越紧、反馈越真实，智能体越靠谱。

**各司其职：模型做判断，代码做确定性的事。** 凡是有确定算法的事（执行命令、检索、解析、状态管理、参数校验），交给 harness 里的普通代码，别让模型去「脑补」——那既慢又不可靠。把模型留给它真正擅长的：语言、推理、判断。

**工具少而精，描述胜过数量。** 与其给二十个功能重叠的窄工具，不如给几个组合性强、边界清晰的工具。工具的**描述写得好不好**，对效果的影响不亚于 prompt。

**验证，而非信任。** 模型会编造、会越权、会重复犯错。危险动作前先校验、先确认、先 dry-run。这一点和软件工程里「质量护栏」意义上的 harness 殊途同归——**都是在「行动前先把关」**。

**保持简洁，别过度脚手架。** 这点最反直觉：把流程写成僵硬的固定链路（第一步必须干嘛、第二步必须干嘛），反而会**把一个聪明的模型关进笼子**。模型越强，越应该把决策权还给它，harness 只做必要的支撑。借用「苦涩的教训」（The Bitter Lesson）的精神——**别用人工脚手架去替代模型本可以自己做好的判断**。

## 常见误区

::: warning 常见误区

- **「换个更强的模型就行了」**：模型是上限，harness 决定你离上限有多近。同模型不同 harness，差距巨大。
- **「harness engineering 就是写好 prompt」**：prompt 只是其中一个零件，循环、工具、上下文、护栏都不是 prompt 能覆盖的。
- **「上下文给得越多越好」**：窗口有限且注意力会衰减，塞太多反而稀释重点。要精选，不要堆砌。
- **「把流程写死最可控」**：过度固化的脚手架会限制强模型的发挥；该放权时要放权。
- **「模型输出可以直接拿去执行」**：不校验、不设权限，迟早被一个幻觉操作坑到。
  :::

## 选型：harness ≠ prompt ≠ 微调

把 AI 效果寄托在单一手段上是误区，三者定位不同、互相配合：

| 手段 | 改变什么 | 迭代速度 | 成本 | 适合解决 |
| --- | --- | --- | --- | --- |
| Prompt engineering | 一次请求里的措辞 | 极快 | 极低 | 单轮输出的质量与格式 |
| Harness engineering | 模型外的整套系统（循环/工具/上下文/护栏） | 快 | 中 | 让模型在真实环境里**自主、可靠地干活** |
| 微调 / 换模型 | 模型本身（「大脑」） | 慢 | 高 | 提升能力上限、注入领域知识 |

理想的组合是：**用对的模型打底，用 harness 把它接进真实世界、管好上下文与安全，用 prompt 打磨每一次具体交互。** 当下，性价比最高、最被低估的那一环，往往是中间的 harness。
