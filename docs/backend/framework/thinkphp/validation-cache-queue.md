# 验证、缓存、队列与事件

ThinkPHP 项目的稳定性不只来自能访问接口，还来自输入校验统一、缓存边界清楚、耗时任务异步化、事件解耦得当。

## 验证器

验证器把规则从控制器中抽出来：

```php
class OrderValidate extends Validate
{
    protected $rule = [
        'sku_id' => 'require|integer',
        'quantity' => 'require|integer|gt:0',
        'remark' => 'max:500',
    ];

    protected $scene = [
        'create' => ['sku_id', 'quantity', 'remark'],
    ];
}
```

控制器只调用验证场景。这样新增接口时可以复用规则，也能单独测试异常输入。

## 缓存

缓存适合读多写少、实时性要求不高的数据：

- 字典配置、系统参数。
- 首页聚合数据。
- 权限菜单。
- 短时间热点查询。

缓存设计要回答三个问题：

1. key 如何命名，是否包含租户、语言、用户维度。
2. 什么时候失效，是 TTL、主动删除，还是版本号。
3. 缓存穿透、击穿、雪崩如何处理。

不要为了减少一次 SQL 把所有数据都缓存。缓存引入的是一致性复杂度，只有热点明确时才值得加。

## 队列

队列适合：

- 发送短信、邮件、站内信。
- 导入导出。
- 图片处理。
- 第三方系统同步。
- 支付回调后的非核心动作。

Job 必须幂等。比如发券任务可以先检查 `coupon_grants` 是否已存在唯一记录，再决定是否发放。不要假设队列只执行一次，重试、超时和 Worker 重启都会导致重复执行风险。

## 事件

事件适合把主流程和附属动作拆开：

```php
event('OrderPaid', $order);
```

订单支付成功后，主流程更新订单状态，监听器处理通知、积分、审计和统计。如果监听器失败不应该影响支付状态，可以放进队列异步执行；如果必须强一致，就不要异步。

## 日常落地建议

1. 校验规则集中到 Validate，不在 Controller 里写一堆 if。
2. 缓存 key 统一命名，避免同一数据多套 key。
3. 队列任务加唯一业务约束，保证幂等。
4. 事件命名用业务事实，如 `OrderPaid`，不要叫 `SendMessageEvent`。
5. 对缓存失效和队列重试写测试或至少写清楚流程。
