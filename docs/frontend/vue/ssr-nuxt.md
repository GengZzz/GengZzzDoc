# Vue SSR 与 Nuxt 入门

普通的 Vue 应用是**单页应用（SPA）**：服务器只返回一个空壳 HTML，页面靠浏览器下载 JS 后再渲染。这带来两个问题——首屏要等 JS 下载执行完才有内容（**白屏**），以及搜索引擎爬虫看到的是空页面（**SEO 差**）。本篇要回答的是：服务端渲染（SSR）如何解决这两个问题、它的代价是什么，以及 Nuxt 为什么能让 SSR 变得可用。

## 痛点：SPA 的首屏与 SEO

```text
SPA 的过程：
浏览器请求 → 返回空 HTML + JS → 下载 JS → 执行 → 才渲染出内容
                                  ↑ 这段时间用户看到白屏，爬虫看到空页面
```

对营销页、博客、电商详情页这类**重内容、重 SEO**的站点，这是硬伤。

## SSR 原理：服务端先渲染，客户端再「激活」

服务端渲染（Server-Side Rendering, SSR）的思路是：**在服务器上先把组件渲染成完整的 HTML 字符串**返回给浏览器，用户立刻能看到内容、爬虫也能抓到。然后浏览器下载 JS，把这份静态 HTML「接管」过来，绑定事件、恢复响应式——这个过程叫 **hydration（激活/注水）**。

```text
SSR 的过程：
浏览器请求 → 服务端渲染出完整 HTML → 浏览器立刻显示内容（首屏快、可被爬取）
          → 下载 JS → hydration 激活 → 之后像 SPA 一样交互
```

关键概念是**同构（isomorphic）**：同一套组件代码，既在服务端跑一遍（生成 HTML），又在客户端跑一遍（激活）。

::: warning 常见误区
正因为代码会在服务端执行，**不能在 `setup` 或组件渲染期间直接访问浏览器专属 API**（如 `window`、`document`、`localStorage`）——服务端没有它们，会直接报错。这类逻辑要放到 `onMounted`（只在客户端执行）里。
:::

## Nuxt：把 SSR 的复杂度封装掉

手写 SSR 要自己处理服务端入口、客户端入口、数据预取、状态同步、路由匹配……非常繁琐。**Nuxt** 是 Vue 的上层框架，把这一整套封装成约定：

- **约定式路由**：`pages/` 目录下的文件自动成为路由，无需手写配置；
- **开箱即用的 SSR**：默认就是服务端渲染，无需自己搭同构；
- **数据获取**：用 `useFetch` / `useAsyncData` 获取数据，框架自动处理「服务端取一次、客户端复用、不重复请求」；
- **多种渲染模式**：同一个项目可按页面选择渲染策略。

```vue
<script setup>
// Nuxt 中获取数据：服务端渲染时取一次，hydration 时复用结果
const { data: posts } = await useFetch('/api/posts');
</script>
```

## 渲染模式：不是只有 SSR 一种

| 模式 | 何时渲染 HTML | 适合 |
| --- | --- | --- |
| SSR | 每次请求时在服务端渲染 | 内容实时变化、需 SEO（电商、资讯） |
| SSG（静态生成） | 构建时一次性生成静态 HTML | 内容不常变（博客、文档站） |
| SPA | 全部在浏览器渲染 | 后台管理系统等无 SEO 需求 |
| ISR（增量静态再生） | 构建生成 + 按需后台更新 | 量大但更新不频繁的页面 |

## 取舍：SSR 不是免费的

SSR/Nuxt 解决了首屏与 SEO，但代价真实存在：

- 需要一个**持续运行的 Node 服务器**（SPA 只需静态托管），运维与成本更高；
- 调试更复杂——要同时考虑服务端和客户端两套环境；
- 不是所有项目都需要：**后台管理系统这类无 SEO 需求的，SPA 足矣**；纯内容站用 **SSG** 往往比 SSR 更省心。

先问自己「我到底需不需要 SEO 和极致首屏」，再决定要不要为 SSR 付出这份复杂度。
